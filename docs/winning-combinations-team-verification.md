## 원인과 수정

- 실제 원인은 경우 A: DB winner_team_id와 result_type이 NULL이었으며 메인 순위는 점수 fallback으로 승패를 계산했다. camelCase 매핑 오류는 아니다.
- 9월 9일의 관리자 PATCH 소스(af56fc9/4bb8431)는 팀/점수/status/scheduled_at/updated_at만 UPDATE했다. winner_team_id와 result_type은 UPDATE 대상에 없었다.
- 2026-09-11 커밋 d00ca2e에서 PATCH에 결과 유형/승리팀 저장이 추가됐지만 기존 9월 9일 데이터는 보정되지 않았다. DB created_at/updated_at도 이 수정 이전이다.
- 당시 standings.getWinnerId는 유효한 저장 승리팀을 우선하고 없으면 점수를 비교했다. HomePage/LeagueDetailPage의 isWinner 역시 점수 비교로 강조했다.
- 최초 필승조합은 요청된 명시적 승리팀 필수 규칙에 따라 SQL의 winner_team_id IN (team_a_id,team_b_id)와 JS 필터로 누락 경기를 제외했고, 점수도 SELECT하지 않았다. 이로 인해 조회 기준이 달랐다.
- 이번에는 공통 gameWinner.resolveWinnerTeamId를 순위/승리기여도/필승조합에 적용했다. 유효한 DB 승리팀 우선, NORMAL(legacy NULL 포함) 완료 경기의 유효한 비동점 점수 fallback, 그 외 null. FORFEIT/TIEBREAK는 점수만으로 추정하지 않는다.
- 관리자 POST에도 누락이 남아 있었다: resultType을 validate에 전달하지 않아 현재 검증에서는 400을 반환하며, INSERT에도 result_type/winner_team_id가 빠져 있었다. 생성 경로의 검증 인자와 저장 컬럼을 모두 수정했다.
- POST/PATCH는 resolveWinnerForSave를 사용한다. NORMAL 비동점은 과거 승리팀이나 클라이언트 입력보다 새 점수로 계산한 승자를 저장한다. 동점/몰수/승부결정의 명시적 승자 검증과 SCHEDULED 결과 초기화는 유지했다.
- DB 스키마 변경 없음. 보정 전 원본 JSON을 backups/에 보관하고 행 잠금과 트랜잭션으로 확인된 3건만 수정했다. 운영 경기 점수/참가팀/날짜/출석은 변경하지 않았다.
